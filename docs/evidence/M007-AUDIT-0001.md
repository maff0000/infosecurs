## What the Auditor personally attempted to break, and could not

- **Tier spoofing** — 6 forged vectors (`?tier=3`, `?package=PRO`,
  `X-Infosecurs-Tier`, `X-Package` headers, a forged cookie, a forged POST
  body) against a real PAUSED-tier live session: all 6 → `403`; Home
  (Tier 0) remained reachable, nothing else did.
- **Session tampering** — 5 distinct live mutations of a real
  `infosecurs_context` (bool-type tier confusion exploiting `True == 1`,
  wrong schema version, subject mismatch, tier/code mismatch, out-of-range
  tier, a missing field) — every one produced a `302` redirect to login,
  fail-closed, never access.
- **Tenant/object isolation** — a real PRO-tier session for a user who is
  a member of `org_a` only, probed against `org_b`'s asset list, a
  specific `KeyAsset`, Home, and security-state (all `404`), plus the
  harder case: a valid `org_a` URL prefix carrying an object ID that
  actually belongs to `org_b` (KeyAsset/Risk/Workplace) — also all `404`,
  never `403` (correctly never leaking existence).
- **Session fixation** — a pre-seeded, attacker-chosen session cookie
  before login; the real login response issued a genuinely different,
  server-generated key.
- **Logout replay** — a real session cookie captured, real POST logout,
  the old cookie replayed against 4 protected routes — all `302`;
  independently confirmed via the ORM that the server-side session row was
  genuinely **deleted**, not merely marked unauthenticated.
- **CSRF** — a POST to `/accounts/logout/` and to a workplace-create
  endpoint with no CSRF token — both `403`, served by the branded
  `403_csrf.html`.
- **XSS** — an organisation literally named
  `<script>alert(1)</script><img src=x onerror=alert(2)>`; on Home and
  Foundations, the raw payload never appeared, only its HTML-escaped form.
  Also ran the product's own 45 real-Chromium Playwright tests
  (execution-flag + DOM based) — all passed.

## Findings

**Critical / High: none.**

**Medium:**
- **M1 — no GitHub branch protection configured on `main`.** Confirmed
  directly by both the Auditor and, independently, the PL
  (`gh api repos/maff0000/infosecurs/branches/main/protection` → `404
  "Branch not protected"`). The 6 "required" CI checks are therefore
  procedural, not GitHub-enforced — they did all pass for this exact
  candidate regardless. This is a repository-governance matter, not a
  code defect in M007, and does not by itself warrant RED/STOP under the
  PID's own severity rules. **Returned to Central Architecture for an
  explicit decision** (enable branch protection or accept as-is) —
  neither the Auditor nor the PL enabled it unilaterally.

**Low (Auditor's own recommendation for all four: accept as documented residual):**
- **L1.** `shell.js`'s overlay-click drawer-close does not return focus to
  the hamburger button (the Escape-key close path is unaffected) —
  already disclosed by the PL as a `strict=True` xfail
  (`core/tests/test_wi6_sidebar_drawer_acceptance.py::
  test_overlay_click_returns_focus_to_toggle`); independently reproduced
  by the Auditor, who watched it fire exactly as expected. See
  `docs/evidence/M007-BROWSER-ACCEPTANCE.md` for the full diagnosis and
  the two fix attempts already tried and ruled out.
- **L2.** `test_static_asset_served_over_real_http_under_production_
  settings` does not pass `secure=True` to the Django test client, so
  `SecurityMiddleware`'s genuinely-active `SECURE_SSL_REDIRECT` 301s it
  before it ever reaches WhiteNoise — a test-authoring gap, not a product
  defect. The Auditor independently proved the underlying behaviour is
  correct (`client.get(url, secure=True)` → `200`, correct `Content-Type`,
  served from the real collected/hashed manifest). Recommend the test
  itself add `secure=True` in a future small fix.
- **L3.** The single shared `Dockerfile` bakes dev/test dependencies
  (pytest, Playwright, etc.) into the same image the release artifact
  uses, and the release compose stack still runs Django's own dev server
  rather than a production WSGI server. Pre-existing from M006, explicitly
  out of scope per PID §43/§41's own "production-readiness remains NOT
  AUTHORISED" — not a regression introduced by M007.
- **L4.** `organisations:list`/`:create` and the auth/identity pages
  still extend `templates/base.html` rather than `application_shell.html`
  — architecturally defensible (no sidebar content is meaningful before an
  organisation is selected) and consistent with the PID's own auth-page
  carve-out, though the carve-out text names auth pages specifically, not
  org-list/create by name. A minor documentation-precision gap; confirmed
  no hamburger/sidebar/entitlement-navigation logic is duplicated
  anywhere as a result.
- **L5 (transparency note, not really a defect).** At the exact frozen
  SHA, three of the required evidence files
  (`M007-RELEASE.md`/`M007-SECURITY-REGRESSION.md`/
  `M007-PL-IMPROVEMENT-SUGGESTIONS.md`) did not yet exist in the tree —
  they landed three commits later, purely additively. The Auditor
  mechanically confirmed the exact delta (`git diff fb5be593..7763341`:
  3 new files, 572 insertions, 0 deletions, 0 modified files) — precisely
  the evidence-only scenario the post-audit delta doctrine sanctions as
  preserving a verdict, and cross-checked that the landed documents'
