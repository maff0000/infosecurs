## 1. What was built

A new Django app, `security_tasks` — confirmed, before writing anything, that no app of that name existed anywhere in the codebase (`grep` across `config/settings.py`'s `INSTALLED_APPS` and the repo root).

### 1.1 Models (`security_tasks/models.py`)

- **`SecurityTask`** — UUID pk, `organisation` FK (indexed, CASCADE), `task_kind` (9-value governed enum: `foundation_confirm`, `foundation_remediate`, `risk_review`, `remediation_followup`, `policy_review`, `evidence_review`, `supplier_review`, `assurance_followup`, `manual_other`), `title`/`summary`, `priority`/`priority_reason`, `status`/`status_reason`/`version` (optimistic concurrency), `assigned_to`/`created_by`, `source_origin`/`source_kind`/`source_object_id`/`source_version`, `occurrence_key`, `idempotency_key`, `due_at`/`review_window_start_at`/`source_timezone`, `completed_at`/`completion_evidence_source_kind`/`completion_evidence_source_object_id`/`closed_reason`, timestamps.
  - `task_group` (Foundations / Risks & Actions / Policies / Evidence & Assurance / Other) is a **derived Python property** (`group_for_kind`), never a stored column — the same discipline `risk_register.Risk.score`/`.risk_band` already use, so a group can never desynchronise from the kind that determines it.
  - Partial unique constraint `securitytask_unique_occurrence_key` on `(organisation, source_origin, task_kind, occurrence_key)` where `occurrence_key IS NOT NULL`.
  - Independent partial unique constraint `securitytask_unique_idempotency_key` on `(organisation, idempotency_key)` where `idempotency_key IS NOT NULL` — a deliberately separate dedupe axis from `occurrence_key` (data contract §1: "manual_other idempotency uses a separate user-supplied idempotency token, not a hardcoded global title dedupe").
  - Index on `(organisation, status, due_at)`.
- **`SecurityTaskDependency`** — UUID pk, `organisation` FK, `predecessor_task`/`successor_task` FKs (both CASCADE), `relation_type` (`blocks`). DB-level `UniqueConstraint` on `(predecessor_task, successor_task, relation_type)` and a `CheckConstraint` rejecting self-reference (mirrors `entitlements.models.ProductArea`'s own "cannot parent itself" precedent exactly). Cross-org rejection, duplicate-edge rejection and cycle rejection all live in the service layer, inside the same transaction as the write — a Postgres `CHECK` cannot express a cross-row-join or graph-cycle constraint.
- **`SecurityTaskEvent`** — UUID pk, `organisation`/`task` FKs, `action` enum, `actor_type`/`actor_user`, `previous_status`/`new_status`, `revision`, `request_id` (idempotency correlation), `metadata` (bounded JSON), `event_time` (auto_now_add). Append-only by convention (no update/delete entrypoint exists anywhere in `security_tasks.services` or `admin.py`).

### 1.3 Allowlisted source registry (`security_tasks/source_registry.py`)

A plain Python dict (`SOURCE_LOCATOR_REGISTRY`), the same shape/discipline as `entitlements.capabilities.ROUTE_NAMESPACE_TO_CAPABILITY` — six registered kinds today: `key_assets.keyasset`, `risk_register.risk`, `remediation.remediationaction`, `policy.policyversion`, `evidence.evidenceitem`, `security_baseline.baselineanswer`. Every resolver filters by the organisation (or the correct FK hop, for `BaselineAnswer` which has no direct `organisation` FK) **before** returning anything — `resolve_source_locator` cannot distinguish "wrong organisation" from "does not exist" to its caller, matching this codebase's established non-disclosing convention. `strict=True` (used by `create_task`/`transition_task` before persisting) raises `UnregisteredSourceKindError` for any kind not in the registry; `strict=False` (used by `get_task_detail` when displaying an already-persisted task) instead renders "Source unavailable". No generic `get_object`/arbitrary-model-name path exists anywhere.

### 1.4 Service layer (`security_tasks/services.py`)

`get_task_list`, `get_task_detail`, `create_task`, `transition_task`, `assign_task`, `link_task_dependency` — exactly the six names the data contract's §3 "suggested canonical contracts" names. Every function takes an already membership-checked `organisation` as its first argument (the same convention `risk_register.services.generate_draft_risks` and `evidence.link_services.link_evidence_to_control` already use) — capability/tier checking stays at the view/decorator layer (`@require_capability()`), exactly like every other app in this codebase; this package did not invent a second authorization mechanism. Two checks the service layer DOES re-run itself, live, on every call, because they are object-scoped and a caller could otherwise forge them in a POST body:
- `assignee_id` must be a **current** `OrganisationMembership` of the organisation — re-queried fresh every call, proven in `test_tenant_isolation.py::TestForeignOwnerAssignmentAttempt::test_revoked_membership_is_rejected_on_next_assignment` (assign succeeds, membership is revoked, the identical assignment is re-attempted and rejected).
- A `source_kind`/`source_object_id` pair must resolve, through the registry, to a real object owned by the organisation, before persistence.

Concurrency (data contract §4):
- `create_task` wraps the insert + its `created` event in one `transaction.atomic()`; a genuine collision on either unique constraint is caught as `IntegrityError` and resolved by re-fetching the existing row under the same organisation (`_find_existing_for_retry`) — never a new occurrence/idempotency key minted on retry.
- `transition_task`/`assign_task` take `select_for_update()` on the task row and compare `expected_version` before writing; a stale caller gets `ConcurrentModificationError`, never a silent overwrite. `transition_task` also replays an already-applied `idempotency_key` as a no-op (no second event).
- `link_task_dependency` locks both endpoint task rows and the organisation's **entire existing dependency-edge set** (`select_for_update()`), so two requests that would together close a cycle cannot both succeed.

Dependency-blocked completion: `transition_task` refuses a move to `done`/`awaiting_review` while an unresolved "blocks" predecessor exists, unless `override_blocked=True` is explicitly passed (a human override, recorded in the event's metadata alongside the mandatory `reason`).

## 3. Concurrency — real proof, not sequential-call simulation

`security_tasks/tests/test_concurrency.py` uses genuine OS threads with `@pytest.mark.django_db(transaction=True)` (the exact precedent `risk_register/tests/test_narrow_viewport_regression.py` already sets for anything needing real cross-thread commits), with a `threading.Barrier` to force actual overlap:

| Test | Result |
|---|---|
| Two threads calling `create_task` with the identical `occurrence_key` simultaneously | **Exactly one row, exactly one `created` event.** Both callers' returned objects have the same `id`. |
| Two threads calling `transition_task` on the same task with the same `expected_version=1` simultaneously | **Exactly one `"ok"` outcome and one `"conflict"` (`ConcurrentModificationError`).** Final task state: `version=2`, exactly one `status_changed` event — never double-applied. |
| (deterministic, non-threaded) repeated `create_task` with the same `occurrence_key` | Second call returns the first row's `id`, with its *original* title — proves the `IntegrityError`-catch-and-refetch path independently of thread scheduling. |
| `transition_task` called twice with the same `idempotency_key` | Version advances to 2 once; the identical repeated call returns the same state with no second event (`test_services.py::TestTransitionTask::test_repeated_idempotency_key_does_not_duplicate_event`). |
| Double-submit of the "create task" web form with the same hidden idempotency token | One row created (`test_http_ui.py::TestTaskCreateFlow::test_double_submit_with_same_token_creates_one_task`). |

All five ran GREEN on first execution against real PostgreSQL in the disposable stack.

## 12. Honest disclosures / design decisions the PID left ambiguous

1. **Pagination shape**: the data contract's own illustrative `get_task_list` signature names a `cursor` parameter; this implementation uses page-number pagination (`page`/`page_size`) instead, for simpler, more reliably testable server-side pagination. Cursor-based pagination can be substituted later without changing the view/template contract, since `TaskPage` is an internal dataclass.
2. **`idempotency_key` for a human web-form submission**: the data contract requires `idempotency_key` on every `create_task` call but does not prescribe how a browser-driven form obtains one. This implementation generates a fresh UUID4 on the GET that renders the create form and round-trips it through a hidden field, so a double-click/browser-retry resubmission reuses the same token; a fresh page load gets a fresh token. Proven in `test_http_ui.py::TestTaskCreateFlow::test_double_submit_with_same_token_creates_one_task`.
3. **`task_kind` restricted to `manual_other` on the customer-facing "New task" form**: the other eight kinds are reserved for deterministic-rules-engine/IRENE-origin creation (M010D/M010C, later packages) — matches M010A PID §2's own "do not create tasks just by visiting page" and M010-MASTER-ARCHITECTURE.md §6's "no automatic task generation until M010D". The service layer (`create_task`) itself accepts any registered kind; only this package's own form narrows it.
4. **`StatusReason`/`ClosedReason`/`PriorityReason` enum values**: the data contract requires these fields to exist as "reason enums" but does not enumerate their values. A small, documented set was chosen (visible in `security_tasks/models.py`) covering the lifecycle transitions this package's own tests exercise; a later package extending the state machine (e.g. M010D's scheduler) may need to add values, which is additive (new choices, not a schema change to the field itself).
5. **CI curation of `security_tasks`' own tests**: explicitly left for Central Architecture/Gunnar to decide (§10.4) rather than this package unilaterally choosing a split across `ci/unit`/`ci/integration`.
6. **7 skipped / 1 xfailed in `ci/integration`, and the +6 passed vs. baseline (§10.3)**: neither investigated to a root cause beyond confirming zero new failures and identical skip/xfail counts — disclosed as open rather than silently absorbed into "GREEN".
