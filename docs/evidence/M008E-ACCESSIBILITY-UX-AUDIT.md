## The key audit question

**Does INFOSECURS now feel like one coherent, commercially credible SME SaaS application rather than a collection of separately-developed Django modules?**

**Yes — with one minor pre-existing (non-blocking, out-of-scope) observation noted in §6.** The component vocabulary established in WI1 (typography scale, two-step radius scale, token-named colours, `.badge`/`.alert`/`.empty-state`/`.progress`/`.option-card`/`.dev-panel`/button variants) is now applied consistently across every one of the 18+ authorised surfaces, not just the three WI1 checkpoint pages. Concretely:

- **Every full-width list-style card across the product now shares one radius step.** Before this PR, `.asset-card`, `.risk-card`, `.evidence-card`, `.action-card`, `.state-card` (and the brand-new `.workplace-card`, `.question-row`) all used the small `--radius` (6px, the step reserved for controls/chips/inputs per the SKILL.md §8 two-step scale) instead of the panel/card step `--radius-lg` (12px). This PR moves all of them onto `--radius-lg`, in six separate files, each carrying an identical, cross-referencing code comment explaining the same defect class. The result: a risk card, an evidence card, a remediation action card and a workplace card are now visually indistinguishable in weight/geometry from a security-state card or a policy panel — exactly the "one system" test. Before this PR, a careful eye moving between Evidence and Workplace would have seen two subtly different card roundnesses; now there is one.
- **Stage 1–3 of the guided Foundations journey now read identically to Stage 4.** Previously Stage 4 alone used the shared `.progress` component and folded "Stage N of 6" into the page subtitle; Stages 1–3 used a page-family-specific `.stage-indicator`/`.stage-progress` pair that existed nowhere else in the product. This PR retires both classes (confirmed: zero remaining template consumers, `grep`-verified) and brings Stages 1–3 onto the exact same `.progress`/`.page-header__subtitle` pattern Stage 4 already used. A novice user moving Stage 1 → Stage 4 no longer experiences a visual "seam" between two differently-built parts of the same journey.
- **Tables exist as a real, designed component for the first time.** `policy/approve.html` and `policy/version_detail.html`'s "Implementation status" tables previously rendered with zero CSS of their own — plain, unstyled, browser-default `<table>` markup that did not reflow and read nothing like the rest of the product (confirmed: `grep` for `.table` in `app.css` before this PR returns nothing). This PR adds a real `.table`/`.table-wrap` component (header shading via `--color-surface-sunken`, consistent padding from the spacing scale, a horizontal-scroll safety net rather than letting the page itself widen). This was the single most visible "looks like internal Django tooling" surface in the two Policy pages, and it is now fixed.
- **Status/colour semantics are now actually enforced where they were previously violated.** `questionnaire/response_detail.html` had, before this PR, three literal hardcoded hex colours (`#e6eefb`/`#185ea8` for "superseded" — a fifth status colour the doctrine never defines; a near-duplicate one-digit-off copy of the warning tokens for "CONFIRM") completely disconnected from the design-token system every other page's badges already read from. This PR replaces all of them with the named `--color-neutral-*`/`--color-warning-*` tokens, so "superseded" (a workflow state) is correctly neutral-grey rather than an invented fifth colour, and "needs confirmation" is correctly the product's one real amber rather than a token-system near-miss that would silently drift out of step with any future palette refresh. This is exactly the kind of defect a whole-product reviewer, not a page-by-page one, is positioned to catch.
- **Governance roles gained real status signalling it previously lacked entirely.** "Not yet assigned" was previously plain, unstyled text; it now carries a real neutral-grey `.badge` ("Not assigned") alongside the existing green "Assigned" badge for active assignees — and, correctly per the doctrine, does **not** invent a severity colour for a role simply being unfilled (the one genuine gap — an assignment to someone now inactive — correctly keeps its separate, pre-existing `.message--error` alert rather than being given a third, overlapping badge colour for the same fact). This is a case where the Implementer's own comment shows real engagement with the doctrine's semantics, not just mechanical class-swapping.
- **The reset-confirmation page finally matches its own entry points.** Home and the Organisation hub already rendered the Customer Zero reset affordance as an unmistakable dashed-border `.dev-panel` with a "Dev" tag (WI1); clicking through to the actual confirmation page — where the one truly irreversible action in the whole product lives — previously landed on a page still styled as an ordinary plain `.summary-card`, with the submit button still `.button--primary` rather than `.button--destructive`. This was a real, user-visible consistency gap: the two signposts told the user "this is dangerous," then the destination quietly said "this is routine." This PR fixes exactly that seam, with no change to the copy, the confirmation input's semantics, or the view's own fail-closed gate (independently re-verified at runtime, see `M008E-BROWSER-RESPONSIVE.md` §5).

## 1. Visual hierarchy, typography, spacing

Consistent across every surface exercised: one `<h1>` per page in the 1.75rem/700 scale, one plain-language subtitle beneath it, `h2` section headings at 1.25rem/600. No surface in this PR introduces a second heading convention, a new type size, or an eyebrow label (the doctrine's explicit anti-pattern, §3/§8 of the skill file) — spot-checked directly against the full `app.css` read, not just the diff. Spacing uses the existing `--space-1`..`--space-5` scale throughout every new/changed rule in the diff; no raw pixel values were introduced (confirmed by reading every CSS block in the diff — the only literal pixel values anywhere are pre-existing ones this PR did not touch).

## 2. Primary vs secondary action clarity

Every page retains exactly one `.button--primary` (or, for the one destructive action, `.button--destructive`) as its visually strongest control; everything else is `.button--secondary`. The reset-confirm button fix (§ above) is the one place this PR actively improves action-hierarchy signalling rather than merely preserving it. No page in this PR's diff introduces a second competing primary action.

## 3. Form usability / guided-question consistency

Stage 1–3's progress presentation now matches Stage 4's; the Customer Assurance "paste one question" form (`questionnaire/list.html`) moved from raw inline `style="width: 100%"` textareas/inputs with no shared class to the standard `.field`/`.textarea`/`.input` components — meaning its focus ring, border colour and sizing now behave identically to every other form input in the product instead of independently. Login's two inputs gained the shared `.input` class for the same reason (no visual change claimed or found; this is a token-consistency fix, verified by reading the `.input` rule in `app.css`, which sets border/padding/radius/focus identically to what a bare unstyled `<input>` would already look close to, so the visible delta is small but the component-discipline win is real).

## 4. Tables / lists / empty states

Addressed in the "key audit question" section above (`.table`/`.table-wrap`, the six-file radius harmonisation). Empty-state handling is also now more consistent: plain, un-styled `<p>No X yet.</p>` lines on `security_state/detail.html`, `policy/detail.html`, and `evidence/detail.html` ("No evidence linked...", "No policy draft...", "Replaces: none") are now wrapped in the shared `.empty-state` component, matching the dashed-border/centred treatment every other genuinely-empty list in the product already used. A second, correctly-distinguished need was found and solved properly rather than forced into the wrong component: `risk_register`'s two explanatory-prose blocks ("how this list is generated") are not empty-state messages and would read badly centred, so this PR adds a real `.empty-state--left` modifier instead of another one-off inline `style="text-align: left"` — exactly the PID §E8 "avoid inline-style proliferation" instruction, applied correctly rather than mechanically.

## 5. Status badges / colour-independent meaning

Every badge on every surface this audit exercised carries real text, never colour alone — independently confirmed live (not just by reading the template): `BADGE_TEXTS questionnaire_response_accepted: ['ACCEPTED', 'SUPPORTED']`, `BADGE_TEXTS governance_roles: ['ASSIGNED', 'NOT ASSIGNED']`. The questionnaire badge-colour-token fix (§ above) is the one place this PR corrects an actual doctrine violation (an invented fifth colour) rather than merely extending the existing, correct four-colour vocabulary.

## 6. Minor observation — not a defect in this PR's diff, noted for completeness

`.dev-panel` (the Customer Zero dev-only affordance, introduced in WI1 and reused unchanged by this PR) is styled using the `--color-warning-bg`/`--color-warning-text` tokens for its dashed border and "Dev" tag. The doctrine (SKILL.md §7) says a dev-only affordance "is never styled using the green/amber/red/neutral status vocabulary... a dev affordance is not a security status" — and structurally it genuinely isn't confused with one (dashed border + explicit "Dev" tag + its own `.dev-panel` class, never reusing `.badge`/`.alert--warning`), but it does *reach for the same colour values* as the amber/warning semantic rather than a visually distinct fifth hue. This is a WI1-era design choice, outside this PR's own diff (confirmed: `app.css`'s `.dev-panel` rule is unchanged by this PR), so it is not a finding against PR #99 and does not affect the verdict — recorded here only because a whole-product review should not pretend not to have noticed it, and because the Delivery Controller may want to park it as a future one-line polish (a dedicated `--color-dev-*` token pair) rather than act on it now.

## 7. Mobile presentation (375px) and keyboard behaviour

Covered exhaustively, with real measurements, in `M008E-BROWSER-RESPONSIVE.md` §2–4: zero horizontal overflow across 31 surfaces × 3 widths; genuine, measured focus-ring changes on every interactive element spot-checked, including the one new destructive-button state this PR introduces.

## 8. Perceived commercial quality — overall verdict

Before this PR, a reviewer moving through the full application would have hit at least three visibly "unfinished internal tool" moments this audit specifically confirmed: an unstyled HTML table on both Policy pages, a plain-card-weight inconsistency between list-style surfaces across six different apps, and a reset-confirmation page that visually undersold the one genuinely dangerous action in the product relative to its own entry points. This PR closes all three, using only the existing component vocabulary (no new design language, no new dependency — confirmed via the earlier `requirements*.txt`/`package.json` zero-diff check), and does so with evidence discipline that **actively found and fixed real defects** (the hardcoded/near-duplicate hex colours; the unstyled Workplace/Questionnaire card classes referencing component names with no matching CSS at all) rather than presenting a narrative-only "it's done" story. The product reads as one coherent system end to end; this audit's own independent measurement did not find a surface this PR touched that still reads as a separately-developed module.
