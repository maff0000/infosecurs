## 1. What was built

A new Django app, `foundations_journey` — confirmed, before writing anything, that no app of that name existed. A thin, validated adapter over the existing, UNMODIFIED `security_baseline.{catalogue,structured_catalogue,stage4,forms,models,services,views}` and `entitlements.metrics` contracts (all read in full before writing a line of this package's own code).

### 1.1 Models (`foundations_journey/models.py`)

- **`JourneyCheckpoint`** — UUID pk, `organisation` FK (CASCADE), `user` FK (CASCADE), `journey_code` (default `"foundations"`), `stage_code`, `current_question_key` (nullable), `pending_task` FK to `security_tasks.SecurityTask` (`SET_NULL`), `checkpoint_state` (5-value enum: `new`/`active`/`waiting`/`paused`/`journey_complete`), `methodology_version`, `last_domain_revision` (a cheap `"<reviewed>:<still_need_confirmation>"` fingerprint, never raw answer content), `last_interaction_at`, `version` (optimistic concurrency). `UniqueConstraint` on `(organisation, user, journey_code)`.
- **`UserJourneyPreference`** — `user` OneToOne (CASCADE), `auto_open_enabled`, `resume_modal_enabled`. Deliberately carries **no** FK to `Organisation` at all — a cross-organisation UI preference, not a journey fact. See §5 for why this keeps it correctly out of the M008A reset manifest.
- Migration `foundations_journey/migrations/0001_initial.py` — generated by `manage.py makemigrations foundations_journey`, not hand-written. `makemigrations --check --dry-run` → `No changes detected` immediately afterward.

### 1.2 Service layer (`foundations_journey/services.py`)

- `get_registered_route` — the only place this app builds a URL; always `django.urls.reverse()`, never string concatenation.
- `get_foundations_question(organisation, user, question_key) -> StructuredQuestionViewModel` — assembles `question_key`, approved title/question/why-it-matters (`security_baseline.stage4.QUESTION_COPY`), the current offered option list (`security_baseline.stage4.offered_options`, a fresh call every time), the user's saved option (`AnswerSelectionDetail`), the exact JML confirmation-checkbox requirement/label (read off a live `StructuredAnswerForm` instance rather than re-typed), stage index (4 of 6), question index (1-12), the 12-control reviewed/confirmed pair (`stage4_progress`), the 18-item completion (`entitlements.metrics.get_security_foundations_completion`), the deterministic `explainer_for` text, and the registered manual-page link.
- `submit_foundations_option(organisation, user, *, question_key, option_code, confirmation=False) -> AnswerReceipt` — reconstructs `StructuredAnswerForm` against a FRESH `offered_options()` call (never a stale option list), and only on success calls `security_baseline.services.record_structured_baseline_answer` — the exact same canonical write path `security_baseline.views.foundations_question` already calls. Returns a receipt whose `next_question_key` is the ACTUAL next-unreviewed control recomputed from the just-committed real state (mirroring `foundations_start`'s own logic), never a hardcoded "next in catalogue order".
- `offer_foundations_followup_task(organisation, user, *, question_key, idempotency_key) -> SecurityTask` — explicit, separately-invoked task handoff (never a side effect of the two functions above). Re-reads the CURRENT canonical answer fresh; raises `NoFollowUpTaskAvailableError` for YES/NOT_APPLICABLE or an unanswered control. Calls `security_tasks.services.create_task` with `source_origin=SourceOrigin.HUMAN`, `source_kind=SOURCE_KIND_BASELINE_ANSWER`, `source_object_id=<the real BaselineAnswer pk>`, and a deterministic `occurrence_key` (`"foundations:<key>:<answer>:<option_code>"`) — deduplicated by `create_task`'s own partial unique constraint.
- `get_journey_checkpoint`/`update_checkpoint` — see §3.

No model in this package is ever written outside these functions; no view constructs `BaselineAnswer`/`AnswerSelectionDetail`/`SecurityTask` directly.

## 2. Required evaluation — manual vs. guided parity (PID §6/§7)

**This is the single most important result in this package.**

`foundations_journey/tests/test_parity_golden_set.py::TestManualVsGuidedParity::test_identical_canonical_effects_on_separate_organisations` parametrizes over **every single (control, option_code) pair** in the real, live `security_baseline.structured_catalogue.STRUCTURED_OPTIONS` table — **57 cases total** (programmatically derived: `sum(len(STRUCTURED_OPTIONS[k]) for k in CATALOGUE_KEYS) == 57`, asserted at module import time so the golden set can never silently shrink), not a representative subset — including:

- All 12 Stage-4 controls, every offered option code each one defines.
- Duplicate canonical-answer pairs with distinct meaning (e.g. `BACKUPS_RESTORE_UNTESTED` vs. `BACKUPS_COVERAGE_PARTIAL`, both derive `partial` but are asserted as two DIFFERENT, correctly-distinct test cases).
- The JML `NOT_APPLICABLE` + confirmation-checkbox path (`JML_NOT_APPLICABLE`, submitted with the confirmation flag, against a profile with `people_with_system_access_count=1`).
- The confirmed-no-remote-access `NOT_APPLICABLE` path (`REMOTE_ACCESS_NOT_APPLICABLE`, against a profile with `has_remote_or_offsite_access="no"`).
- Every `*_NOT_SURE`/UNKNOWN option code.

For each case, the SAME `(question_key, option_code)` is submitted through (a) the real HTTP `security_baseline:foundations_question` view and (b) `foundations_journey.services.submit_foundations_option`, on **two separate, freshly-created fixture organisations** with identical `OrganisationProfile` facts, and the test asserts:

- `BaselineAnswer.answer` identical on both sides, and equal to the receipt's own `derived_answer`.
- `AnswerSelectionDetail.option_code`/`.methodology_version` (provenance) identical on both sides, and equal to the receipt's own fields.
- `security_baseline.stage4.stage4_progress(assessment)` (the 12-control reviewed/still-need-confirmation pair) identical on both sides.
- `entitlements.metrics.get_security_foundations_completion(organisation)` — percentage, completed_count, total_count — identical on both sides.

**Result: all 57 golden-set cases PASS. 59 passed, 0 failed** (`test_parity_golden_set.py` in full — 57 parametrized golden-set cases + the re-answer test + the full-twelve-control-run test below, run against real PostgreSQL in the disposable stack).

Three further, non-parametrized tests in the same module close remaining PID §6 scenarios on the SAME two-path comparison shape: re-answering an existing selection (submit twice through each path, same final answer/option, row counts stay at 1 on both sides), and a full, realistic 12-control run reaching identical final stage-progress/completion on both paths. `foundations_journey/tests/test_forgery_and_edge_cases.py` closes the remaining golden-set scenarios that are NOT a parity comparison by nature (a rejection has no "canonical effect" to compare — both paths must simply reject and write nothing): stale/forged/unoffered option_code (direct service-layer and HTTP-level), a profile fact changing between render and submit, cross-tenant, unauthenticated, and wrong-tier (`TIER_PAUSED` denied with a 403, mirroring `entitlements/tests/test_decorators.py`'s own established pattern via its `set_session_tier` helper).

**Concurrent multi-tab**: `foundations_journey/tests/test_concurrency.py` uses genuine OS threads (`@pytest.mark.django_db(transaction=True)` + `threading.Barrier`, the same precedent `security_tasks/tests/test_concurrency.py` already established) — two simultaneous `submit_foundations_option` calls for the same answer leave exactly one `BaselineAnswer`/`AnswerSelectionDetail` row; two simultaneous `update_checkpoint("pause")` calls with the same `expected_version` produce exactly one winner and one `ConcurrentCheckpointModificationError`.

## 3. Checkpoint design and its test coverage

`get_journey_checkpoint` is READ-ONLY — it recomputes the live position (next-unreviewed control, derived `CheckpointState`) directly from `AnswerSelectionDetail` every call, but never persists an advance merely from being read (proven: `test_checkpoint.py::TestCheckpointReadNeverWrites` — repeated reads never bump `version`). The checkpoint is only EVER advanced in storage by `_persist_reconciled_position`, called strictly after a successful `record_structured_baseline_answer` commit — proven: answering one control bumps `version` from 1 to exactly 2, never more.

Because the stored `current_question_key` is always freshly re-derived from the real answers rather than trusted from any client input, there is no client-settable "jump to question N" write for two browser tabs to race — the one genuinely client-triggered transition (`pause`/`resume`, via `update_checkpoint`) uses real CAS (`expected_version` under `select_for_update()`), proven under genuine thread concurrency in §2 above.

A paused/waiting checkpoint survives a mere reconciling read (`test_checkpoint.py::TestPauseResumeCheckpointTransition`) — never silently resumed just because the journey page was viewed again. A second colleague in the same organisation shares the same real answers but gets their OWN checkpoint row (`test_checkpoint.py::TestCheckpointIndependentPerUser`); removing their membership makes the guided route an ordinary 404, same as every other organisation-scoped route in this codebase.

## 9. Honest disclosures / design decisions the PID left ambiguous

1. **`idempotency_key` for `submit_foundations_option`**: the data contract's illustrative signature names an `idempotency_key` parameter; this implementation does not require one, because the underlying write (`record_structured_baseline_answer`) is already naturally idempotent via `update_or_create` — resubmitting the identical option_code is a no-op change-wise, and resubmitting a DIFFERENT option_code is a legitimate, intentional "change answer" action, not a duplicate to dedupe. Adding a second, independent idempotency ledger on top would have been exactly the "duplicated write path" the PID elsewhere warns against. `offer_foundations_followup_task` (the one write in this package with a genuine create-vs-duplicate distinction) DOES take `idempotency_key`, matching `security_tasks.services.create_task`'s own required parameter.
2. **`source_origin=SourceOrigin.HUMAN` for a follow-up task offered through an IRENE-rendered card**: chosen deliberately over `SourceOrigin.IRENE` — the task is always created by an explicit person clicking a visible button, never an autonomous model decision; IRENE is a UI surface here, not an actor. `security_tasks.forms.TaskCreateForm`'s own docstring ("the other eight kinds are reserved for deterministic/IRENE-origin creation... no automatic task generation until M010D") was checked carefully against this choice — it is about AUTOMATIC creation merely from viewing a page, which this package explicitly never does (a separate POST is always required); it is not a prohibition on a later package using a non-`manual_other` kind through its own explicit, human-triggered endpoint.
3. **Checkpoint reconciliation strategy**: the data contract asks for "read and reconcile with real domain answer on resume" without prescribing the mechanism. This implementation chose to NEVER trust a stored `current_question_key` as authoritative — it is always recomputed fresh from `AnswerSelectionDetail` on every read, and only persisted after a real write. This is a stronger reading than strictly required (a cached-and-occasionally-reconciled position would also satisfy the letter of the contract) but was chosen because it makes the "two tabs cannot regress each other" concurrency property true by construction rather than by a race-prone compare-and-set on the question key itself.
4. **Stage 1-3/5-6**: deep-link inventory only (§6), per the PID's own explicit triage instruction.
5. **Pause/Resume UI**: a minimal Pause/Resume button pair was added to the guided card itself so the required browser-acceptance scenario (pause, resume, confirm correct resume question) could be driven through a real UI action rather than only the service layer directly — the richer IRENE modal chrome around this (tabs, auto-open, etc.) remains M010C's scope.
6. **`foundations_journey/tests/` not added to `.github/workflows/ci.yml`'s curated `ci/unit`/`ci/integration` lists**: the same disposition `M010A-TASK-SPINE.md` §10.4 already established for `security_tasks/tests/` — this package's own suite has a `transaction=True` threaded test (`test_concurrency.py`) and a Chromium-dependent test (`test_browser_acceptance.py`), each with real infrastructure requirements the current `ci/unit` job does not provision at all. Ran as its own explicit invocation throughout this package (§7.1) — never silently excluded from verification, only from the curated `ci.yml` lists pending a Central Architecture/Gunnar decision on how to split it (likely: `test_models.py`/`test_parity_golden_set.py`/`test_forgery_and_edge_cases.py`/`test_checkpoint.py`/`test_task_handoff.py`/`test_zero_ai_calls.py` → `ci/unit`; `test_concurrency.py`/`test_browser_acceptance.py` → alongside the other Chromium/`transaction=True`-dependent tests in `ci/integration`).
