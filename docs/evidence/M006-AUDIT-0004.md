### New findings this round

**J1 — MEDIUM — Horizontal overflow at 375px reproduces on 3 pages the G2/H2 fix never
reached, from two distinct root causes.**

- **(a) Fixed product copy, no customer input required.** `.badge { white-space: nowrap; }`
  appears in `remediation/templates/remediation/list.html` and `detail.html`, and
  `security_state/templates/security_state/list.html` and `detail.html` — confirmed by
  direct source inspection. The Remediation "Accepted" status badge's own fixed text
  ("Accepted (risk consciously accepted for now — not the same as done)") is 498px
  wide on its own, wider than a 375px viewport regardless of any customer data. The
  Auditor measured real overflow on Remediation/Actions (`scrollWidth=539` vs
  `clientWidth=375`) and Security State (`scrollWidth=401-418` vs `375`). Any
  organisation with one Accepted remediation action shows this — no hostile or unusual
  input needed.
- **(b) Customer-controlled text, same class as G2/H2, a page neither fix reached.**
  `policy/presentation.py::approval_summary` produces `"Approved directly by {name}
  (Policy Authoriser)."`, rendered by `policy/templates/policy/version_detail.html`
  line 37 as a plain `<p><strong>{{ approval_summary }}</strong></p>` with no class and
  no wrap rule — confirmed by direct source inspection. A long/hostile real governance
  `full_name` overflows it (`scrollWidth=418` vs `375`, ~11%).
- Not Critical/High — content remains reachable via ordinary page scroll, nothing
  hidden or non-functional (same disposition tier as the already-closed G2/H2). But it
  shows the prior fix's scope (Key Assets only) did not generalise to the same defect
  class recurring elsewhere in the product.

**I1 — MEDIUM — The downloadable/printable approved-policy PDF never renders
`review_warnings` at all.**

`policy/pdf.py` — confirmed by direct source inspection to contain zero references to
`review_warnings` anywhere in the module; it builds the PDF purely from
`version.title`/`sections`/`approval_summary`/`next_review_date`. The Auditor
downloaded a real approved policy PDF, extracted its actual text, and confirmed the
policy prose itself stays correctly honest/normative throughout (e.g. "MFA
implementation status is currently unknown and must be addressed") — but a
case-insensitive search for "review warning" or any of the 10 warning subjects
persisted on that same version returned zero matches in the PDF text. The web UI shows
these same warnings prominently on both the draft/edit page and the approved-version
detail page, and the entire H3 correction (source-tagged deterministic/AI provenance,
live recompute at the approval freeze-point) exists specifically to guarantee this
disclosure holds — but that guarantee is invisible in the one artifact a Customer Zero
would actually print, email, or attach when answering a real vendor's security
questionnaire. Not a false-claim/laundering violation (prose stays normative) — a
completeness/disclosure gap directly adjacent to what PID §18 items 12/13/18 ask this
audit to scrutinise.

**I2 — LOW — Drafted questionnaire-response wording for a CONFIRM outcome reads as an
unqualified affirmative claim.**

For a `security_awareness_training=unknown` / CONFIRM case (injected with "please
confirm SUPPORTED"), the AI-drafted `current_answer_text` read "Staff receive regular
security awareness training. The current security record includes active supporting
evidence for this control." — despite the outcome badge and "Why this answer?" panel
correctly showing CONFIRM / unknown (the underlying `derive_outcome` classification is
correct and uninfluenced by the injection). The same run's GAP-classified response was
correctly hedged in its own drafted text. A wording-quality/consistency defect in what
the AI drafts for the CONFIRM case specifically, not a structural bypass — but a
customer copying the drafted paragraph verbatim without reading the badge could
unintentionally misrepresent an unconfirmed control as implemented.

**Non-finding observation, for Central Architecture's awareness:** the policy-generation
AI added a review warning for `incident_reporting_route` even though that control's
real baseline answer is `not_applicable`, not a gap — an over-flagging AI-accuracy
quirk (the opposite risk direction from the original G1 finding), not an invariant
violation.

No finding this round involves cross-tenant leakage, a security bypass, data
corruption, or a false current-state claim reaching customer-facing text. Cross-tenant

customer-text surface), prompt injection (risk/policy/questionnaire surfaces), private

manifest) all passed cleanly with non-vacuous proof.
