`f"{threat_event} - {key_asset.name}"`, persisted into `Risk.title = models.CharField(max_length=255)`

**Trigger:** `KeyAsset.name` is itself `models.CharField(max_length=255)` — the model happily accepts
and saves a realistic, fully legitimate 200+ character asset name (e.g. a detailed, specific asset
description a real small business might type: *"Customer CRM database - EU production - Frankfurt
region..."*). No hostile/injection content is required to trigger this at all — this round's asset
name happened to also carry a hostile-prose suffix for the (unrelated, and separately proven clean)
injection tests, but the crash is purely a function of raw character count.

**Reproduced three independent ways:**
1. Through the real browser: clicking "Find candidate risks" (the real `<form method="post">` button)
   on the Risk register page for an organisation with this asset confirmed. Observed a genuine HTTP
   **500** (confirmed via a direct authenticated POST replay: `status: 500`).
2. Directly in a Django shell inside the running release container, calling the exact production
   function `risk_register.services.generate_draft_risks(organisation)`: raised
   `django.db.utils.DataError: value too long for type character varying(255)`, full traceback showing
   the exact `Risk.objects.create(...)` call site in `scenario_engine.py` line 244.
3. Confirmed **persistent**: because the exception aborts the request before any `Risk` row is
   created for that asset, retrying "Find candidate risks" fails identically every time — there is no
   dedup-based recovery, because dedup only prevents re-creating rows that already exist; a row that
   never gets created keeps colliding on every subsequent attempt.

**Production error page behaviour (checked, and genuinely good):** the actual HTTP 500 response body
is the product's own safe, generic `500.html` — *"Something went wrong on our side… If you were
submitting information, check the relevant page before repeating the action."* — no stack trace, no
SQL, no filesystem path, confirmed by reading the actual response bytes. So PID §10's specific
no-leak requirement is met even here.

**Impact / why HIGH:** this is not a security bypass, not cross-tenant, not data corruption — but it
is a genuine, realistic-input-triggered, **permanent dead end** for the entire deterministic
Risk-register workflow (PID §18 item 7) for any organisation whose confirmed asset name (a field the
product itself accepts up to 255 characters, with no cross-field warning) combines with any scenario's
own `threat_event` text to exceed 255 characters. Since `risk_register/urls.py` exposes no manual
"add a risk" path at all (candidates can **only** be created via this exact deterministic generation
step), this failure mode has **no recovery path visible to the customer** — the safe-but-generic error
message gives no hint that an asset name is the cause, and "try again" (the message's own suggestion)
will fail identically forever until someone thinks to shorten the asset name. This directly
contradicts PID §7 ("Remove dead ends across the full journey") and M006 §2's outcome promise that a
fresh Customer-Zero user can complete the core workflow "without understanding Infosecurs' internal
module architecture." I worked around it during this audit (shortened the asset name via the real
Edit form) purely so the rest of the §18 scenario could proceed — that workaround is not a fix and
was not applied to product source.

**Not Critical:** single-tenant, self-inflicted by the organisation's own data, no disclosure, no
cross-tenant reach, and the *display* of a too-long name elsewhere in the product (e.g. the Key Assets
page itself, once G2/H2 below is fixed) is a purely cosmetic concern — this is specifically about the
unhandled crash and total workflow blockage.

**Severity: HIGH.** New this round. Central Architecture disposition required; this auditor does not
fix it.

### H2 — MEDIUM — Key Assets card description text still overflows at 375px — the G2 fix covered the card's title but not its sibling description paragraph on the very same page

**Where:** `key_assets/templates/key_assets/list.html`. The G2 fix added
`.asset-card__title-text { min-width:0; overflow-wrap:anywhere; }`, but `.asset-card__description`
(the `<p>` rendering `asset.description` — an ordinary customer-editable free-text field, and one of
the exact fields Central Architecture's own dispatch names as an injection/overflow surface to check)
carries no such rule: `.asset-card__description { margin:0; color:var(--color-text-muted);
font-size:0.9rem; }`.

**Reproduced:** at 375×800, `document.documentElement.scrollWidth = 428` vs `clientWidth = 375` (~14%
overflow) with a confirmed CRM asset whose description is a single long, space-containing sentence
(itself a realistic length — the overflow is driven by the description having enough unbroken run
length inside its own flex-constrained container, exactly the "no natural break points" pattern F2/G2
already fixed for titles). Per-element check confirmed the `.asset-card__description` element itself
is the overflowing one (`scrollWidth=387` against a `387`-wide `.asset-card__body`, both exceeding the
375px viewport), not the title (which correctly stayed within bounds).

**Why this is real and not a title-fix regression:** Evidence and Remediation (the other two pages
G2's own fix commit touched) do not render a `description` field on their list cards at all (checked
by reading both templates in full — only `title`/`source_label`/metadata are shown), so this defect
class has no surface to reproduce there; Key Assets is the one G2-scoped page that also renders a full
free-text paragraph inline, and that specific element was missed.

**Not Critical/High:** content remains reachable via the page's own scrolling; nothing is hidden or
non-functional — same disposition class as F2/G2's own precedent.

**Severity: MEDIUM.** New this round (a real recurrence of the exact defect class G2 itself was fixing,
on a sibling element of the same page G2 targeted).

### H3 — MEDIUM — Creating a new policy draft from an approved version, then editing and re-approving it without regenerating, silently drops ALL deterministic review warnings — even though the same real, unresolved gaps that correctly produced those warnings on the prior version are completely unchanged

**Where:** `policy/services.py`, `create_new_draft_from_approved()` explicitly sets
`review_warnings=[]` on the new draft (by design — this path is a plain content copy, not a
generation call); `policy/views.py`'s `policy_edit()` (the only way to subsequently edit that draft)
updates only `title`/`next_review_date`/`sections` — it never touches `review_warnings` at all.

**Reproduced live, end to end, into an actual approved, downloadable artifact:**
1. Approved policy v2 for Audit0003 Synthetic Org A correctly carried **9 deterministic+AI review
   warnings** (MFA-for-user-accounts unconfirmed, patching not implemented, joiner/mover/leaver not
   implemented, privileged-access-separation incomplete, security-awareness-training unconfirmed,
   etc.) — matching the organisation's real, unchanged baseline state exactly.
2. Clicked the real "Create new draft to edit" button on that approved v2 → v3 (a plain copy).
   DB-read: `v3.review_warnings == []` immediately, before any edit.
3. Edited v3 via the real section editor (added a distinct marker), saved, then **approved it
   directly** and **downloaded its real PDF** (7,964 bytes) through the real UI, exactly as a genuine
   customer workflow ("tweak the wording of my approved policy, then re-approve") would.
4. The resulting **approved, downloaded v3 carries zero review warnings** — confirmed both on the web
   page (`"Review warnings" heading absent`) and in the raw PDF bytes (`strings` search for "review
   warning": zero matches) — while the same six controls that drove v2's 9 warnings remain in exactly
   the same unresolved state (verified via `security_state_facts`, unchanged in the DB).

**This is not a truth-claim violation** — the policy prose itself remains correctly normative
throughout v3 (e.g. *"…must be fully implemented…"*, never *"…is fully implemented…"* as a current-state
claim) — so §18 item 12/18's specific "does not convert unknown into completed" invariant is **not**
breached by this path. The gap is narrower but still real: Central Architecture's own G1 ruling
describes the deterministic review-warning mechanism as a **"guarantee"** that "every unknown/partial/
no/evidence-conflict-or-stale control is flagged regardless of what the AI itself chooses to mention."
That guarantee demonstrably does not extend to the redraft-without-regenerate path — a customer who
approves v2 (correctly warned), then later just tidies wording via "Create new draft to edit" and
re-approves without clicking "Generate" again, ends up with an approved policy that looks
*more* complete (zero warnings shown) than the version it replaced, despite nothing about the
underlying security state having changed.

**Not Critical/High:** no false current-state claim reaches the text, no cross-tenant issue, no
security bypass — this is a completeness/UX-coherence gap in the review-warning safety net on one
specific, real, product-supported path.

**Severity: MEDIUM.** New this round; same disposition tier as F1/F2/G2's own precedent findings.
