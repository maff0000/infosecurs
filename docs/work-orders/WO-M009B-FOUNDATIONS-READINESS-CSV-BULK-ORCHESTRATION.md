## 0. What this Work Order implements

The accepted amendment (hereafter "the amendment") established: a deterministic, 100%-threshold Foundations Assurance Readiness gate enforced at the correct point in the request pipeline; a separate question-level answerability signal; a hardened CSV V1 contract; a genuinely atomic bulk-processing claim-and-persist mechanism requiring one narrowly scoped M005 extract-method refactor; and a machine-composition answer-quality contract with explicit, non-human-attributed audit provenance. This Work Order turns that architecture into four bounded, independently testable, sequentially-dispatched implementation increments.

**M005 remains the sole questionnaire truth engine throughout.** No increment in this Work Order alters `questionnaire.grounding`, `questionnaire.outcome`, the AI orchestration modules, or the `QuestionnaireQuestion`/`QuestionnaireResponse` schema, except the one named, bounded, behaviour-preserving refactor in Increment 2.

### 2.2a C1 — exact CSV structural-validation and extraction routing, read directly against the real M009A code before specifying this

Direct reading of `questionnaire/import_services.py` confirms the Architect's finding precisely. Today, `ingest_questionnaire_import` (lines ~91-178) hardcodes `file_format=QuestionnaireImport.FILE_FORMAT_XLSX` unconditionally, and rejects any upload where `is_zip_shaped` is `False` immediately — a genuine CSV (plain text, never ZIP-shaped) is **always** rejected at this exact point today, before `security_gate.run_container_gate` or `xlsx_extraction.extract_candidates` are ever reached. Both of those two functions are themselves OOXML/ZIP-specific and do not apply to CSV content at all. Fixing this requires **routing on an explicit, caller-declared format, independently verified against the real bytes — never routing on content-sniffing alone, and never trusting the declaration blindly:**

1. **`ingest_questionnaire_import` gains `declared_format` (`QuestionnaireImport.FILE_FORMAT_XLSX` or `FILE_FORMAT_CSV`)**, supplied by the view based on which upload action the customer used (two buttons/forms, or one form with an explicit format selector — a Work-Order-stage UX detail, not an architectural one). `QuestionnaireImport.file_format` is set from this declared value, not hardcoded.
2. **The early non-ZIP rejection becomes format-conditional, not removed:** if `declared_format == FILE_FORMAT_XLSX` and the bytes are not ZIP-shaped, reject exactly as today (byte-for-byte unchanged XLSX path — M009A's own existing test suite must still pass unmodified against this branch). If `declared_format == FILE_FORMAT_CSV` **and the bytes ARE ZIP-shaped**, this is also a deterministic, named rejection (`"declared_csv_but_zip_shaped"`) — a declared-format mismatch is itself hostile/malformed input and must fail closed, never be silently reinterpreted as the other format.
3. **The structural gate dispatches on `import_record.file_format`** inside `_run_gate_and_scanner`: XLSX calls `security_gate.run_container_gate(file_path)` exactly as today; CSV calls the new `csv_import.validate_csv_structure(file_path)`, returning the identically-shaped result object, so every line of code *after* the gate call (the `if not gate_result.accepted:` branch, the scanner invocation, `_transition_to_gate_rejected`/`_transition_to_gate_failed`) needs **zero change** — it already only depends on `gate_result.accepted`/`.reasons`/`.structural_summary`, not on which function produced them.
4. **The scanner step is already completely format-agnostic** (`get_scanner().scan_file(file_path)` operates on raw bytes, confirmed by direct reading) — reused for CSV with literally zero code change. CSV is not exempted from malware scanning merely because it is "plain text" (amendment §4.1, restated here because C1 specifically asked this to be made explicit in the Work Order, not only the amendment).
5. **Extraction dispatches on `import_record.file_format`** inside `_run_extraction`: XLSX calls `xlsx_extraction.extract_candidates` exactly as today; CSV calls the new `csv_import.extract_candidates`, returning the identically-shaped `ExtractionOutcome`.
6. **`retry_security_gate` requires no change at all** — it already dispatches via `_run_gate_and_scanner`, which now itself branches on the already-persisted `import_record.file_format`; a CSV import that reached `security_gate_failed` (scanner `UNAVAILABLE`/`ERROR`) retries through the identical code path, now correctly re-running CSV structural validation (idempotent — a prior CLEAN structural result is not cached across a retry, mirroring the existing XLSX behaviour exactly) and the scanner, unchanged.

**Preserves the XLSX path unchanged**, as required: every existing M009A XLSX test, fixture, and evidence document remains valid without modification — the dispatch is additive, never a rewrite of the existing branch.

### 2.6 FORGE implementation instructions

**Membership before readiness — the additional contract clarification, made concrete:** the `process_view` hook's first action is the *same* tenant-membership check `get_member_organisation_or_404` already performs (reused directly, or an equivalent membership-only predicate extracted from it if a 404-raising helper cannot be called from middleware cleanly) — a non-member gets a genuine 404 immediately, **before readiness is evaluated at all**. Only once membership is confirmed does the hook proceed to the entitlement-tier check (existing `require_capability` logic, unaffected) and then readiness. This ordering is load-bearing: evaluating readiness before membership would let an unauthenticated or non-member caller distinguish "this organisation exists and is not ready" from "this organisation exists and I'm not a member" from "this organisation does not exist" by response shape — exactly the enumeration this codebase's existing 404-never-403 convention exists to prevent, now at risk of being reintroduced by the new middleware hook specifically if the ordering is not enforced deliberately.

Build the `process_view` hook first (membership → entitlement → readiness, in that order). **The guarantee this hook actually provides, stated precisely per this round's documentation correction:** it prevents Django's own lazy multipart parsing from ever running (so `request.POST`/`request.FILES` are never populated) and prevents any application-level write, storage, or scanning from ever happening for an unready organisation's request — it does **not**, and cannot, guarantee that the underlying WSGI server (Django's own `runserver`, or any reverse proxy/gunicorn worker in front of it in a future topology) has not already read or buffered the raw request bytes off the socket before Django's own middleware chain ever runs; that boundary is owned by the web server, not by Django middleware, and this Work Order makes no claim about it. The required unit test therefore asserts what the hook genuinely controls: that `request.POST`/`request.FILES` are never accessed, no upload handler is ever installed/invoked, and no byte is ever written to `import_storage` for an unready organisation's POST — not a claim about the server's own socket-level buffering. **Also required:** a unit test proving a non-member's request never receives any readiness-shaped response (genuine 404, byte-identical to the existing non-member behaviour on every other organisation-scoped route). Build CSV structural validation and extraction (§2.2a) second, reusing every bounded-limit numeral M009A's XLSX path already established (10 MiB upload ceiling, etc.) unless this increment's own measurement shows a CSV-specific number is required. Do not touch `questionnaire.catalogue`/`grounding`/`outcome` at all in this increment.

### 4.5a Required measurement task and daily AI-invocation accounting — do not guess, per the Architect's explicit instruction, moved and extended per C3

**Distinguishing a configured ceiling from measured reality, explicitly:** `ai_platform.gateway.DEFAULT_TIMEOUT_SECONDS = 30.0` (confirmed by direct reading) is the *maximum any single call to the gateway is permitted to take* before the client's own socket times it out — it is a **configured upper bound**, not a description of how long calls actually take. No empirical measurement of the real, currently-configured AI gateway's actual interpret+draft latency has been taken in this architecture/Work-Order pass, and this Work Order does not invent one in its place.

**Separately, neither `docker-compose.yml` nor `docker-compose.release.yml` configures any server-level request timeout** — both run `python manage.py runserver` in every topology this project has today (confirmed by reading the `Dockerfile` and both Compose files directly); this is this project's own already-documented Beta-stage characteristic (`docs/delivery/BUILD-REPRODUCIBILITY.md`'s own M006 PID §12 finding), not a new discovery this Work Order treats as a defect to fix.

**The required task, with `CLAIM_TTL`'s derivation path made explicit:**
1. Measure real interpret+draft latency (p50/p95/p99) against the actual configured AI gateway, inside a disposable stack, for a representative sample of real or realistic questions — recorded with real numbers in the durable evidence document, not estimated.
2. **`CLAIM_TTL`'s primary basis is the measured P99 end-to-end latency (step 1) plus a safety margin — never the theoretical worst-case bound alone.** The theoretical worst-case (up to 2 calls × up to 2 attempts each × `DEFAULT_TIMEOUT_SECONDS` = 4 × 30s = 120s) is retained only as a secondary sanity ceiling — if measured P99 plus margin would exceed it, that is itself a signal the retry/timeout configuration needs the Architect's attention, not a reason to silently adopt the larger number. Conservative starting default pending measurement: **180 seconds** — explicitly provisional, superseded the moment real measurement data exists.
3. **Daily per-organisation AI-invocation admission/reservation, corrected per C4 — a plain `count()` is not sufficient.** The first draft's `AIInvocationRecord.objects.filter(...).count()` check is a genuine time-of-check-to-time-of-use race: two concurrent requests for the same organisation can both read a count below the ceiling, before either has actually consumed any of that capacity, and both proceed — exceeding the real ceiling. The corrected mechanism, **reusing only tables that already exist** (no new model, no new infrastructure, per the Architect's explicit instruction to avoid both):

   - **`MAX_AI_INVOCATIONS_PER_CLAIM = 4`** (interpret: 1 initial + 1 bounded retry; draft: 1 initial + 1 bounded retry — the exact worst case already established for `CLAIM_TTL`'s own derivation) is the fixed, worst-case *reservation* every single claim makes against the daily budget, decided at claim time, before any AI call runs.
   - **Admission check, inside `claim_next_eligible_question`'s own existing short transaction**, serialised per organisation via a transaction-scoped Postgres advisory lock (`SELECT pg_advisory_xact_lock(hashtextextended(<organisation_id>, 0))` — a single raw SQL call, automatically released at the transaction's commit/rollback, blocking only *other concurrent claim attempts for the same organisation*, never a different organisation's work): `consumed = AIInvocationRecord.objects.filter(organisation=organisation, started_at__gte=<start of UTC day>).count()` (unchanged from the first draft — every record regardless of `status`, so a failed/pending attempt still counts) **plus** `reserved_in_flight = QuestionnaireBulkResponseAttempt.objects.filter(organisation=organisation, outcome="claimed", claimed_at__gte=<start of UTC day>).count() * MAX_AI_INVOCATIONS_PER_CLAIM` (the worst-case budget every *currently in-flight, not-yet-finalised* claim for this organisation today has already reserved — reusing `QuestionnaireBulkResponseAttempt`, the model this Work Order already introduces in Increment 3, rather than a second ledger). If `consumed + reserved_in_flight + MAX_AI_INVOCATIONS_PER_CLAIM > DAILY_AI_INVOCATION_CEILING`, the claim attempt is refused — **returning a distinct, machine-readable `BudgetExhausted` result, never `None`/the same signal as "nothing eligible to claim"** (the caller must be able to tell "this organisation has real work queued but is budget-capped" from "this organisation genuinely has nothing left to process" — conflating them, as the first draft did, would hide a real operational condition behind a silent-looking stall).
   - **Reconciliation against actual invocations happens automatically, with no separate reconciliation step**: the moment a claim transitions out of `"claimed"` (to `"succeeded"` or `"failed"`, via the existing finalisation transaction), it stops contributing to `reserved_in_flight` and its real AI calls are now counted via `consumed` instead — the two queries together always reflect the true, current state, never requiring a background job to "true up" reserved vs. actual.
   - **Conservative handling of failures, expiry, and crashes:** a claim that crashes or expires remains `"claimed"` — and therefore still fully reserved against the budget — until the existing opportunistic expiry sweep (§4.1/§6.1a) relabels it `"failed"`. This over-reserves (never under-reserves) during the window between a real failure and its sweep-driven expiry, which is the safe direction: the ceiling can never be silently exceeded by an uncounted crashed claim, at the cost of (at most) one claim-slot's worth of budget sitting reserved-but-idle for up to `CLAIM_TTL` after a crash.
   - **UTC-day rollover, defined precisely:** `<start of UTC day>` is `datetime.now(timezone.utc).replace(hour=0, minute=0, second=0, microsecond=0)`, recomputed fresh on every call (never cached). A claim that happens to straddle midnight UTC is a non-issue in practice, stated explicitly rather than left as an unaddressed edge case: `CLAIM_TTL` is on the order of minutes (§4.5a's own measurement-driven value, with a provisional 180-second default), so a single claim's lifetime can never realistically span a full UTC-day boundary — if a future `CLAIM_TTL` value ever approached 24 hours, this reasoning would need revisiting, but nothing in this Work Order's own numbers comes close.
   - `DAILY_AI_INVOCATION_CEILING`'s exact numeric value remains a Product-Authority-adjacent decision (§6), proposed alongside `CLAIM_TTL` in the same evidence document, not invented here.
4. **New required test, per C4:** a genuine concurrency test — two real concurrent claim attempts for the same organisation, with `DAILY_AI_INVOCATION_CEILING` set just below what both would together consume if the admission check were not race-safe — asserting that the advisory lock correctly serialises them, that only as many claims as the budget actually allows are created, and that the excess attempt(s) receive `BudgetExhausted`, never a `QuestionnaireBulkResponseAttempt` row that would push real consumption over the ceiling. This is its own named Independent Audit gate, reproduced independently by the Auditor, not only the Implementer's own test.
5. Submit this measurement, the resulting `CLAIM_TTL` proposal, and the proposed `DAILY_AI_INVOCATION_CEILING` for Architect acceptance **before Increment 3 is dispatched** (per §4.5). `DEFAULT_BULK_BATCH_SIZE` (Increment 4 only) is proposed separately, later, once real single-question latency data from Increment 3's own live operation is available to inform it — not guessed now alongside the other two numbers.
